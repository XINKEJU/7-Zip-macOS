顶层仅四个目录，职责边界清晰：


`CPP/` 内部进一步分为三层，这是理解整个代码库的关键：

## 四、核心算法实现分析

### 4.1 压缩算法核心（`C/` 目录）

这是 7-Zip 最具技术价值的部分，采用**纯 C 实现以最大化可移植性与复用性**（LZMA SDK 即由此目录抽出，属公有领域）：

| 文件 | 行数 | 算法角色 |
|---|---|---|
| `LzmaEnc.c` | 3,154 | LZMA 编码器（区间编码 + 自适应概率模型 + 最优解析） |
| `LzmaDec.c` | 1,367 | LZMA 解码器 |
| `LzFind.c` | 1,746 | 匹配查找（哈希链 / 二叉树，编码器性能瓶颈所在） |
| `Lzma2Enc.c` / `Lzma2Dec.c` | 799 / 493 | LZMA2 分块封装层 |
| `XzDec.c` / `XzEnc.c` | 2,863 / 1,374 | XZ 容器格式 |
| `Ppmd7Enc.c` / `Ppmd8Enc.c` | 340 / 337 | PPMd 上下文模型压缩 |
| `Aes.c` | 429 | AES 加解密 |
| `Sha256.c` | 492 | SHA-256 |
| `MtCoder.c` / `MtDec.c` | 604 / 1,124 | 多线程编解码调度 |

设计要点：`LzmaEnc.c` 与 `LzFind.c` 行数居高，说明编码侧复杂度远高于解码侧——这符合 LZMA「压缩比优先」的设计取向，编码器需在价格模型下执行近乎最优的解析搜索。

### 4.2 过滤器链（Filter Chain）

7-Zip 采用**可组合的编码器链**，多个过滤器串联后接主压缩器。已实测支持的过滤器：

| 过滤器 | 用途 |
|---|---|
| `BCJ2`（4 流） | x86 可执行文件分支指令转换，压缩率最优 |
| `BCJ` / `PPC` / `IA64` / `ARM` / `ARMT` / `SPARC` / `ARM64` / `RISCV` | 各架构分支指令归一化 |
| `Delta` / `Swap2` / `Swap4` | 增量与字节序预处理（音频、图像、数据库） |

实测 `7zz i` 输出确认上述编解码器全部编入 arm64 二进制。

### 4.3 加密与完整性

`CPP/7zip/Crypto/`（2,289 行）实现了完整的安全栈：

- **对称加密**：AES-256-CBC（7z）、AES（RAR5）、ZipCrypto / ZipStrong
- **密钥派生**：PBKDF2-HMAC-SHA1（`Pbkdf2HmacSha1.cpp`）
- **认证**：HMAC-SHA1、HMAC-SHA256、SHA3
- **随机源**：`RandGen.cpp`

### 4.4 哈希算法支持（实测）

```
CRC32 / CRC64 / MD5 / SHA1 / SHA256 / SHA384 / SHA512
SHA3-256 / XXH64 / BLAKE2sp
```

## 五、多线程与性能优化

三条并行的优化路径，构成 7-Zip 的性能基础：

1. **汇编优化层（`Asm/`）**：12 个别手写汇编文件，覆盖 CRC32、AES、LZMA 解码、查找匹配、SHA1/256、排序等热点。实测编译日志含 `-DZ7_7ZIP_ASM` 与 `LzmaDecOpt.o`，确认 arm64 路径已启用汇编加速。
2. **多线程编解码（`MtCoder.c` / `MtDec.c` / `Lzma2DecMt.c`）**：采用块级并行 + 匹配查找线程（`LzFindMt.c`）与哈希线程分离的双线程架构。
3. **CPU 特性探测（`CpuArch.c`）**：运行时检测指令集能力，按需启用 SIMD 与 AES-NI 路径。

| 平台 / 工具链 | 入口文件 |

构建变量分离得很干净：`var_*.mak`（路径与编译器）、`warn_*.mak`（告警级别）、`cmpl_*.mak`（组合入口）。

## 七、安全分析

### 7.1 近期安全修复记录（摘自 `DOC/src-history.txt`）

| 版本 | 日期 | 安全事项 |
|---|---|---|
| **26.03** | 2026-09-03 | **CVE-2026-58052**：解压特制归档时未能保留 Mark-of-the-Web 标记 |
| 26.02 | 2026-06-25 | **CVE-2026-14266**：XZ 解压堆缓冲区溢出，可致远程代码执行 |
| 26.00 | 2026-02-12 | ZIP / CPIO / RAR / UFD / QCOW 逻辑改进；修复 TAR 稀疏文件解压缺陷 |
| 25.01 | 2025-08-03 | **CVE-2025-55188**：重写符号链接处理逻辑以强化解压安全 |

评估：近四个版本**每个版本都包含至少一项安全修复**，其中 26.02 的 XZ 堆溢出属 RCE 级别。这印证了归档解压器作为「不可信输入解析器」的高风险属性。

### 7.2 代码内建的防护机制（已核实存在）

1. **路径穿越防护** — `CPP/7zip/UI/Common/ExtractingFilePath.cpp` 中 `Correct_PathPart()` 显式识别并清空 `"."` / `".."` 路径分量，`Correct_FsPath()` 提供 `absIsAllowed` 开关控制绝对路径是否放行。
2. **MotW 传播** — `NExtract::NZoneIdMode` 枚举与 `IFolderSetZoneIdMode` / `IFolderSetZoneIdFile` 接口（见 `Guid.txt` 第 12–13 号接口），配合注册表项 `WriteZoneIdExtract`，即为 CVE-2026-58052 的修复落点。
3. **符号链接加固** — 25.01 起引入的解压期链接处理策略。

### 7.3 风险提示

- RAR 相关代码（`CPP/7zip/Archive/Rar/`、`Compress/Rar*`）源自 unRAR，**许可证明确禁止用于重建 RAR 压缩算法**。
- `C/ZstdDec.c`（4,067 行）与 `Archive/ApfsHandler.cpp`（4,470 行）为较新引入的大型第三方格式解析器，属攻击面增量区域。
- 建议：任何基于该源码库的产品化改造，均应将「跟随上游 CVE 修复」纳入固定维护流程。

## 九、结论与建议

### 架构评价

该代码库是**工业级归档软件工程的范本**，三点值得借鉴：

1. **C/C++ 混合分层的务实取舍** — 性能与复用敏感的核心算法用纯 C 实现（可抽为库、可跨编译器、可被第三方集成），业务逻辑与 UI 用 C++ 实现（获得抽象能力）。这一分界使 LZMA SDK 能被 Linux 内核、Python、Rust 等生态广泛复用。
2. **汇编与 C 的双实现策略** — 每个热点模块保留 C 版本与汇编版本，通过 `USE_ASM` 宏切换。既保证可移植性（无汇编写法时仍可构建），又能在目标平台拿到极限性能。
3. **构建系统的变量化设计** — 通过 `.mak` 文件的多层 include 组合，同一套源码支撑 4 类工具链 × 17 个产物，避免为每个组合维护独立工程文件。

### 若需二次开发，建议路径

| 目标 | 建议入口 |
|---|---|
| 集成压缩能力到自有程序 | 直接使用 `C/` 目录（公有领域），编译为静态库 |
| 新增归档格式支持 | 参照 `Archive/ArHandler.cpp`（较简洁）实现 `IInArchive` 接口 |
| 新增压缩算法 | 在 `Compress/` 下实现 `ICompressCoder` 并注册到对应 `*Register.cpp` |
| 裁剪体积 | 修改 `Bundles/` 下目标产物的 `.mak`，移除不需要的 `*Handler.o` |
| 构建 GUI 版本 | 仅 macOS/Linux 用 `Alone2`（7zz）；GUI 依赖 Win32，须在 Windows 编译 |
